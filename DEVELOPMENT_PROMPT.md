# NihonCode development prompt — Phase 2 (data remediation)

## 0. Mission

You are the implementation agent for NihonCode (キタ) Phase 2, data remediation. Phase 1 (MVP) shipped and its Definition of Done was verified with evidence; the Phase 1 prompt lives in git history (HEAD `4e870ee` and earlier). Your job is implementation_plan.md section 2: build the content pipeline that turns untrusted raw `data/` into a validated `data/clean/`, triage every defect into fix/replace/exclude with a human-review queue where judgment is required, resolve JLPT audio aliasing, consolidate attribution, and update the measured ledger. Phase 2 gates Phase 3. Do not start Phase 3: no level selector, no JLPT practice UI, no conjugation drill, no N4–N1 enablement in the app, no SRS statistics page, no export/import. The app keeps reading the raw-data gate exactly as Phase 1 shipped it; Phase 2 proves `data/clean/` is correct and equivalent-or-better on N5, and Phase 3 swaps the loaders. Scope discipline is part of the job.

Read in this order and keep them as authority throughout:

2. `docs/data-quality.md` — the **measured** defect ledger. Every count you act on comes from here or from `npm run audit:data -- --json`; never from PRD prose (definitional deltas are documented there).
3. `PRD.md` section 18 — the owner's defect statement. Owner-authored: you report deltas, you never edit it.

5. `docs/decisions.md` — decision log. New decisions get an entry there in the same change.
6. `docs/quality.md` — what is already proven by executable evidence, and the open gap ledger you are closing.
7. `scripts/audit-data.mjs` + `scripts/data-baseline.json` — the frozen raw-data baseline and the gate that protects it.
8. `data/generated/*`, `data/jlpt/*`, `data/generated/practice_core.json` — untrusted source content. Inspect shapes; never trust field values.

Surface briefs and `mockup.png` are not authority in Phase 2: there is no UI work. If the owner directs a curation UI mid-phase, the Phase 1 design contract (git history) and `docs/design-system.md` bind it.

## 2. Hard constraints

- Non-goals stay binding: no AI features of any kind; no native packaging; no companion apps; no Mastery Path, placement, curriculum maps, or worksheets; no speech recording or pronunciation scoring; no accounts, cloud sync, or server-backed profiles.
- Raw `data/generated/` and `data/jlpt/` are untrusted, read-only. Never hand-edit them. `scripts/data-baseline.json` freezes their structural metrics; any drift fails `npm run check` until deliberately re-baselined (regenerate with `--write-baseline` **plus** a docs/data-quality.md update in the same change, and report the delta to the owner).
- `data/clean/` is generated output. Never hand-edit it either. The only hand-edited curation artifact is the adjudications file (section 4).
- The pipeline runs offline and reproducibly: no network fetches, no downloads, no scraped media, deterministic output bytes for identical inputs and adjudications. Remote-image localization would break all three — see task 5.
- No new runtime dependencies without an owner decision. The pipeline is Node stdlib in `scripts/`, matching the existing guardrail-script convention. `js-yaml` was removed in the Phase 1 closeout audit; do not reintroduce it.
- Stable namespaced IDs (`kana:hiragana:あ`, `kanji:n5:水`, `vocab:n5:水|みず`, `grammar:n5:12`, `jlpt:n5:listening:12:3`). Content-order-independent; clean output stamps them; progress never references positions. Grammar lesson IDs are namespaced **across levels** in clean output (they restart at 1 per level in raw). **ID stability is a hard requirement**: `vocabId` is content-derived (`kanji|kana`), so any remediation that rewrites `kana` (Problem C packed readings) re-keys the entry — and shipped progress rows (`srsCards`, `drillAttempts`, `grammarState`) reference the old key. For every item already graded in Phase 1, the clean ID must be byte-identical, or the same change ships a Dexie migration (db.ts is at `version(3)`; the remap is `version(4)`) that rewrites affected progress rows. Collisions are build failures, not warnings: two entries in one level sharing kanji+kana would silently merge IndexedDB rows, and neither the Phase 1 gate nor the raw audit asserts uniqueness — the clean validator must (task 1).
- Do not auto-approve pedagogical correctness. Normalize structure in code; route sense, answer-key, and exclusion decisions to the review queue (section 4).
- Never copy direction-contract text (THESIS/OWN-WORLD/STORY/FIRST VIEWPORT/FORM blocks) into any shipped artifact.
- Phase 1 app behavior is pinned: `npm run check`, `npm test`, and `npm run eval` stay green at every task boundary. The audit walks raw `data/` only; `data/clean/` can never register as raw-data drift.

## 3. Pipeline architecture

- `scripts/lib/*.mjs` — pure normalization and detection functions (no fs, no I/O): kana→romaji transliterator, dictionary-marker stripper, packed-reading splitter, grammar-defect detectors, JLPT record classifiers, ID stampers. Unit-tested under Vitest: extend `vitest.config.ts` include to `scripts/lib/**/*.test.mjs`, and give those tests pure-node semantics with a per-file `// @vitest-environment node` docblock (not `environmentMatchGlobs`, which is deprecated in Vitest 3 and logs a warning on every run).
- `scripts/build-clean.mjs` — the driver: reads raw `data/`, applies `scripts/lib` transforms plus owner adjudications, writes `data/clean/` and `data/clean-report.json` (per-fix counts, excluded counts, queue references). `npm run build:clean`. Deterministic: stable key order, no timestamps in content files.
- `scripts/audit-clean.mjs` — the clean-pool validator (implementation_plan.md cross-phase verification): re-measures the defect classes over `data/clean/`, asserts zero on the included pool, and **hard-fails on any duplicate ID within a pool**. `npm run audit:clean`. Keep it a separate script with its own report: `audit-data.mjs`'s `--self-test` pins the live `cleanSlice` gate key set to an exact hardcoded fixture and exits nonzero on any key drift (audit-data.mjs "gate key drift"), so adding clean-pool keys to the raw audit breaks `npm run check` with a key-set error instead of a gate failure. The raw audit stays untouched — it guards raw drift and the Phase 1 clean-slice floors, nothing else. check-arch.mjs classifies any path outside `src/` as external, so these Node scripts reading raw `data/` are not data-gate violations; the data gate binds `src/**` imports only, and `src/content/loaders.ts` keeps importing the raw clean-slice files until the Phase 3 loader swap.
- `data/clean/` is **generated and ignored**, never committed: add `data/clean/` and `data/clean-report.json` to `.gitignore`, and a `gc.mjs` cleanup target with `regenerate: "npm run build:clean"`. `curation/review-queue.json` is generated the same way (ignore it); `curation/adjudications.json` is the one tracked curation file. Any CI or local step that consumes clean data (starting with `audit:clean`, and the Phase 3 app build) runs `build:clean` first — state this in the workflow when you wire it.
- The deleted Phase 1 JLPT validator and romaji→katakana converter are reference material in git history at HEAD `4e870ee` (`src/content/gate.ts` `validateJlptSets`, `src/components/romaji.ts`). The transliterator you need runs the **opposite** direction (kana→romaji); reuse the yōon/digraph tables, don't re-derive them.
- `data/generated/index.ts` (legacy loader, quarantined per docs/data-quality.md "Legacy loader") is deleted as pipeline cleanup — it is reference-only, outside every tsconfig, and the gate owns the type contract. Delete it in task 1's wave and update the ledger row in the same change.

## 4. Curation and review-queue contract

- `curation/review-queue.json` — **generated** on every build: every item needing human judgment, with source file, stable ID, defect class, measured evidence, and a proposed disposition. Never hand-edited.
- `curation/adjudications.json` — **tracked, owner-edited**: map of queue item ID → `fix` (with the corrected value where applicable) | `exclude` (with reason) | `replace` (with the replacement). The build consumes it; an item present in the queue with no adjudication fails the DoD triage gate, not the build (the build excludes unadjudicated items from graded pools and says so in the report).
- Escalation: when a task needs an owner decision (task 2 conjugation source, task 5 localization override, task 6 kana scope, task 7 licensing), stop that task's dependent work, write the decision request into your report with measured counts and options, and proceed on the remaining tasks. Record the resolution in docs/decisions.md when it lands.

## 6. Phase 2 Definition of Done

Mirrors implementation_plan.md Phase 2 DoD, made checkable:

- `data/clean/` builds reproducibly from raw `data/` (byte-identical on re-run) with zero validation errors on the included pool.
- `npm run audit:clean` reports: 0 entries with Japanese in a `romaji` field, 0 kanji answers with dictionary markers in the accepted set, 0 JLPT records with truncated prompts or null keys in the graded pool, 0 unresolved remote-image dependencies in included sets.
- The review queue is triaged: every flagged item is fixed, replaced, or explicitly excluded in `curation/adjudications.json`; nothing ships silently.
- Conjugation metadata: present and spot-checked for the agreed scope, or the scope decision is escalated and recorded with the blocker named honestly (do not mark this done on inference from category buckets).
- The audio evidence table exists and an owner-confirmed sample proves the right audio plays for the right question, or listening is recorded as blocked with the measured evidence.
- Attribution doc exists; licensing cleared or release explicitly blocked with reasons recorded.
- PRD delta list delivered to the owner; docs/data-quality.md, docs/quality.md, and docs/decisions.md updated in the same changes as the counts they record.
- Phase 1 stays green: `npm run check`, `npm test`, `npm run eval` pass at the integrated head with no app-code regressions.

## 8. Verification protocol

Run, in order, at each task boundary and at the integrated head: `npm run check` (typecheck, lint, format, arch, taste, docs, raw-data audit); `npm test` (Vitest incl. `scripts/lib`); `npm run build:clean` twice with a checksum comparison; `npm run audit:clean`; `npm run eval` at any boundary that could touch app behavior, and once at the integrated head. Observed failure → smallest durable guardrail: prefer extending `scripts/check-*.mjs` or the clean audit over prose, then update `.harness/manifest.json`. Fix batches between runs, never per-tweak.
